飞书数字分身 · 方案调研

Posted on 2026-10-21 Views:
Symbols count in article: 5.2k Reading time ≈ 5 mins.

结论先行

不建议从零自建，也不要让同一个 AI 既替你看私信、又对外接待同事。推荐“后台助理 + 前台分身”两层：同事找前台分身就像找你，它用你的知识、按你的口吻答复；后台助理带着你的权限，只替你本人干活。

  1. 后台助理（只服务你）：直接用飞书官方的专属工作伙伴，它在官方选型指南里的定位就是面向个人的数字分身。它能盯关键人和群、起草回复，由你确认后再发。
  2. 前台分身（服务同事）：另建一个“XX 的分身”，只挂你精选的知识和技能，同事私聊或在群里 @ 它。原生用企业工作伙伴（一个 Agent 服务多人，每人每群记忆隔离）；要接内部系统时再自建（飞书机器人 + lark-cli + Eino ADK）。
  3. 你的判断沉淀为技能：代码评审、仓库知识、答复口吻、授权边界都写成 SKILL.md，前后台共用。

三条红线：同事始终知道在和 AI 分身对话；前台分身不持有你的用户权限；承诺、审批、对人的评价只由你本人发出。

先对齐：数字分身要做什么

数字分身和普通助理的区别是“代表你”：同事找它就像找你。所以它必须先回答四个问题。

问题 设计要点
凭什么答（知识） 只用你精选并愿意公开的内容：规范、文档、过往答复、评审技能；不含你的私聊和未公开文档
像不像你（口吻） 从你本人写的文档和发出的消息提炼“答复风格”技能，不拿别人的消息当素材
能做主到哪（授权） 分三档：可直接答、起草待你确认、必须转给你
以谁的身份说话（身份） 默认是标明 AI 的“XX 的分身”机器人；以你本人名义发言只用于你确认过的草稿

分身有两种工作方式：同事直接找分身（前台代答），以及别人找你时由助理替你起草（后台代拟）。两者需要的权限完全不同，下文分开设计。若还想要形象和声音（视频、会议出镜），那是另一层，需你本人授权并按规定标识，本文不展开。

飞书正把 Agent 当作与人并列的协作成员来设计：9 月的飞书 8.0 已支持把 Agent 像同事一样拉进群。产品名在 8 月有一轮调整，下表按时间倒序列出关键节点。

四条路线对比

后台助理首选 A 的专属工作伙伴；前台分身用 A 的企业工作伙伴，或 D 自建；B 适合当你的私人后台，不宜直接对外；C 只适合 FAQ 式分身。

路线 上手成本 定制深度 主要风险 在分身中的角色
A 飞书原生（专属工作伙伴、企业工作伙伴、豆包工作） 最低，开通即用 平台内配置人设、技能、MCP；部分版本可换企业自定义模型 能力边界由平台决定；按 AI 额度计费 专属工作伙伴做后台助理；企业工作伙伴做前台分身
B 开源个人 Agent（OpenClaw、Hermes） 中，需部署运维 极高：模型、Prompt、插件、多渠道 安全面大：高危漏洞、恶意技能、公网暴露；密钥自管 私人后台；单用户记忆，不宜直接对外
C 低代码平台（扣子、Dify） 低到中 中：工作流、知识库、插件 难读个人上下文，多为问答型 FAQ 式前台分身
D 完全自建（机器人 + Agent 框架 + lark-cli） 高 最高，可深度接内部系统 工程投入和长期维护 要接内部系统、需严格评测的前台分身
  • A 飞书原生：官方选型指南的分法是个人用选专属工作伙伴，团队共用选企业工作伙伴，深度定制选飞书 OpenClaw。企业工作伙伴支持 100 人共用一个 Agent、每人每群记忆物理隔离，带变更记录、diff 和一键回滚；凭证集中托管，Agent 不直接持有密钥，正是前台分身需要的。
  • A 的技能复用：豆包工作支持上传本地技能文件夹，要求含 skill.md，且开头有 YAML 格式的名称和描述（帮助中心），与现有 SKILL.md 格式基本兼容。
  • B 开源个人 Agent：飞书 OpenClaw 官方插件走长连接，分“以机器人身份”和“以你的身份”两种模式；后者以你的名义读写文档、搜索消息，官方建议仅限个人使用、不要分享给他人（插件说明）。选型指南还指出 OpenClaw 是单用户记忆体系，不原生支持多人共用而记忆隔离，对外做分身要自己补齐。
  • B 的安全记录：2026 年初曝出多个高危漏洞（含跨站 WebSocket 劫持和命令注入）；官方复盘称 2 月底至 3 月初约 20% 的 ClawHub 技能为恶意或可疑（安全内参）。
  • C 低代码平台：扣子可一键发布为飞书机器人；Dify 需借助 LangBot 等开源桥接接入飞书（Dify 文档）。适合只答规范和流程的 FAQ 式分身，难以替你处理个人事务。
  • D 完全自建：开放平台提供一键创建飞书智能体应用 SDK（Node、Python、Java、Go），扫码即预置收发消息、文档评论、卡片回调等权限和长连接事件。Go 技术栈可选 Eino ADK，与 Kitex 同属 CloudWeGo，提供 ReAct 智能体、多 Agent 编排和中间件。

推荐方案：后台助理 + 前台分身

两层之间隔一道权限墙：后台助理带着你的权限只服务你，前台分身只带精选知识面对同事，两边共用同一套技能。

同事的问题先落到前台分身：能直接答的当场答，其余附摘要推给你，你确认后由分身代发或亲自回复。别人直接找你的消息，由后台助理起草，你确认后再以你的名义发出。

  • 后台助理：专属工作伙伴可主动盯关键人和关键群，每天早上整理未读摘要和待办；上级来消息时可分析意图、补齐背景、起草回复供你参考（专属工作伙伴）。
  • 前台分身：企业工作伙伴挂团队知识空间和你的技能，进群 @ 即用，每位同事、每个群记忆隔离，改动可追溯、可回滚。
  • 深度集成（可选）：自建分身通过 lark-cli 操作飞书、通过内部 MCP 接代码平台和 CI；豆包工作伙伴支持接入开源、第三方和企业自建的智能体，成熟后可与官方 Agent 组队。
  • 本地执行：豆包工作伙伴主体在云端 7×24 运行；任务依赖本地文件、内网或已登录环境时，经飞书客户端在授权范围内调用本机执行（功能手册）。

关键设计点：身份、权限与边界

分身最容易出事的是身份和权限：前台一旦带着你的权限，同事一句话就可能让它读出你的私聊和文档。以下六点按优先级排列。

  1. 身份与告知：前台分身用独立机器人，名称、头像和每条回复都标明是 AI 分身。《人工智能生成合成内容标识办法》自 2025 年 9 月 1 日起施行，要求服务提供者对生成内容添加显式标识（新华网），企业内部也建议照此执行。以你本人名义发消息需同时申请 im:message 和 im:message.send_as_user（发送消息 API），只用于你确认过的草稿。
  2. 权限隔离：前台分身只用应用身份和精选知识空间，不持有你的用户令牌。飞书 OpenClaw 插件对“以你的身份”模式的建议是仅限个人使用、不分享给他人（插件说明）；lark-cli 也建议这类机器人不进群、不让他人使用。
  3. 授权分档与转人：直接答（规范、流程、已公开结论）；起草待确认（评审意见、排期、对外承诺）；必须转你（审批、对人的评价、未决事项、有冲突的话题）。转你时附上下文摘要卡片，你一键确认、改写或亲自回复（卡片回调 card.action.trigger），答复回流成分身知识。
  4. 知识与口吻：知识只取你愿意公开的内容，回答附出处链接，方便同事核对。口吻从你本人写的文档和发出的消息提炼成“答复风格”技能，不拿别人的消息当素材；专属工作伙伴也支持一句话设定名字、头像和说话风格。
  5. 入口与感知：机器人收不到别人发给你本人的私聊，只收到发给分身的单聊、群里 @ 和文档评论 @，用长连接接收即可，不需要公网地址。可在飞书签名或状态里写明“常见问题先问 @XX 的分身”；别人直接找你的消息，交给后台助理盯和起草。
  6. 记忆、审计与下线：每位同事、每个群的对话记忆隔离，事先说明保留期限和可见范围。所有 CLI 调用进飞书审计日志，并区分个人行为与应用行为（飞书 CLI 安全说明）。分身用你的姓名和头像，开关应在你手里，转岗或离职时能随时下线。

结合质量架构岗位的首批场景

先放出问得多、风险低、你最容易验收的场景，下表按建议上线顺序排列。

场景 谁发起 分身做什么 授权档 落点
质量规范与流程答疑 同事私聊或群里 @ 按你的口吻答复，附规范链接 直接答 前台分身
服务与 IDL 知识问答 同事 用仓库知识提取技能沉淀的知识作答，例如某接口的 IDL 在服务仓还是公共 IDL 仓 直接答 前台分身
代码评审预审 同事发评审链接 用你的评审技能先过一遍，标注为预审意见 起草待确认 前台分身 + 评审技能（接仓库需自建或 MCP）
求助分诊 同事 问清背景和紧急度，约时间或附摘要转给你 必须转你 前台分身
关键人消息代拟 别人发给你 分析意图、补齐背景、起草回复 你确认后发 后台助理
每日简报、会议纪要、周报 定时或会后 未读摘要、行动项、周报初稿 你审阅 后台助理

后台部分基本开箱即用：专属工作伙伴已内置盯关键人消息并起草回复、每天早上整理未读和待办等用法。lark-cli 自带会议纪要汇总和站会报告两个工作流技能，可作为周报技能的起点。

落地路线

先把后台助理用起来，再小范围放出前台分身；每过一道闸门再扩大范围。

闸门 1 定下分身该答什么、不该答什么；闸门 2 用你过去真实答过的问题做盲测，看准确率和口吻；闸门 3 要求内测期间零越权。验收指标统一为五项：答复准确率、口吻认可率、该转未转次数、越权次数、每周替你分担的咨询量。

开工前待确认

以下七点决定方案能否落地，建议开工前逐条确认。

  • 公司是否允许以员工名义的 AI 分身答复同事，以及标识方式的要求。
  • 前台分身能否由你本人在企业工作伙伴后台搭建，还是需要管理员开通。
  • 租户的 AI 版本与额度：是否已开通豆包工作伙伴（超出每人每月免费额度需另购）。
  • 哪些知识可以放进前台分身：规范、文档、过往答复各自的公开范围。
  • 开放平台能否申请 im:message.send_as_user，审批人是谁；不行就统一走“你手动发送”。
  • 公司对 OpenClaw 等开源 Agent 的安全政策，以及允许使用的模型。
  • 要接的内部系统清单（代码平台、CI、缺陷平台）及接口形态（API 或 MCP）。
